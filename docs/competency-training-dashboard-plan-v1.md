# 역량 강화 대시보드·훈련 시스템 구현 계획서 v1.0

## 0. 문서 목적과 실행 원칙

이 문서는 개인 학습자의 웹·API 보안 진단 역량을 평가하고, 약점을 근거 기반으로 보완하는 기능의 구현 기준이다.

기능을 한 번에 크게 만들지 않는다. 각 단계는 아래 순서를 반드시 통과한다.

```text
요구사항 고정 → 구현 → 자동 테스트 → 수동 화면 검토 → 데이터 검증 → 단계 검토 → 다음 단계
```

다음 단계는 이전 단계의 완료 기준이 모두 충족됐을 때만 시작한다. 테스트가 없거나 데이터 검증이 누락된 기능은 완료로 간주하지 않는다.

### 0.1 확정된 제품 원칙

1. 기본 진입점은 `/dashboard/역량강화` 하나다.
2. `/dashboard/1`, `/dashboard/2`처럼 의미 없는 경로를 만들지 않는다.
3. 문제·실습·기록처럼 전체 화면이 필요한 기능만 `/dashboard/역량강화/**` 하위 경로를 사용한다.
4. 점수는 단순 정답률이 아니다. 증거 품질, 원인 분석, 조치안, 재검증을 함께 평가한다.
5. AI는 해설·반례·구조화 보조 역할이다. 최종 합격 조건은 케이스별 루브릭과 자동 검증으로 고정한다.
6. 실제 외부 사이트에 자동 진단·공격 요청을 보내지 않는다. 실습은 격리 Docker 환경 또는 정적 케이스에서만 수행한다.
7. API 키·계정·토큰·개인정보는 답안, 피드백, Markdown, 프런트엔드 응답에 저장하지 않는다.
8. 과거 답안과 문제 버전은 삭제하거나 덮어쓰지 않는다. 재시도는 별도 시도로 남긴다.

### 0.2 범위

포함한다.

- 분야별 현재 수준, 신뢰도, 근거, 취약점, 추천 과제를 보여주는 대시보드
- 정적 진단 문제, 보고서 리뷰 문제, 격리 실습 문제
- 문제 보관함, 재시도, 과거 답안 비교, 응용 문제, 개인 메모
- 오개념 기록, 복습 추천, 평가 이력
- 모델별 평가 비용과 호출 이력

포함하지 않는다.

- 임의 외부 URL 자동 취약점 진단
- 실제 고객 시스템을 대상으로 하는 공격 자동화
- AI가 설명 없이 점수를 확정하는 평가
- 원격 공개 실습 서버 운영
- 현재 임시 SQLite 파일을 런타임 DB로 직접 사용하는 방식

## 1. 현재 근거와 출발점

### 1.1 이미 확보된 임시 평가 결과

현재 임시 SQLite 분석 결과에는 다음이 저장돼 있다.

- 직접 수동 검토 청크: 128개
- 정확히 같은 본문으로 확인된 중복 전파 청크: 202개
- 핵심 평가 항목: 21개
- 중복 전파 청크는 점수 계산에서 제외

임시 DB는 `/private/tmp` 아래에 있으므로 서비스의 영구 데이터로 사용하면 안 된다. 1단계에서 MySQL의 사용자 소유 데이터로 이관한다.

### 1.2 초기 평가에서 확인된 방향

강점은 요구사항 정의, 보고서 구조화, 데이터 품질 조건 설정, SQL·Java/Spring·Docker·로그 기반 디버깅이다. 보완 우선순위는 비밀값 관리, 세션·쿠키 보안, 정적 데이터 흐름 추적, 취약 여부를 증거 없이 단정하지 않는 판단 훈련이다.

이 평가는 자격 인증이 아니다. 대시보드는 점수와 함께 근거 수, 신뢰도, 마지막 평가일을 항상 표시해야 한다.

## 2. URL과 화면 정보 구조

### 2.1 라우트

```text
/dashboard/역량강화                 역량 강화 메인
/dashboard/역량강화/문제             문제 보관함
/dashboard/역량강화/문제/:caseId     문제 풀이와 답안 제출
/dashboard/역량강화/실습             격리 실습 보관함
/dashboard/역량강화/실습/:labId      실습 시작, 상태, 초기화, 산출물
/dashboard/역량강화/기록             시도·점수·피드백 이력
/dashboard/역량강화/오개념           반복 오류와 정정 노트
```

`/dashboard/역량강화`는 모든 기능의 출발점이다. 하위 경로는 새 제품이 아니라 메인 페이지에서 선택한 전용 작업 공간이다.

### 2.2 메인 화면 구성

```text
상단: 전체 학습 상태 / 마지막 활동 / 다음 추천 과제 / 주간 목표
좌측: 분야별 역량 카드 그리드
중앙: 추천 훈련 큐와 진행 중인 문제 또는 실습
우측: 반복 오개념, 최근 피드백, 복습 예정
하단: 최근 시도 이력과 역량 변화 그래프
```

각 역량 카드는 다음을 표시한다.

- 분야명과 색상
- 현재 점수와 신뢰도
- 최근 평가일
- 근거 수
- 가장 큰 취약 지점 1개
- 다음 추천 과제 1개

카드에 마우스를 올리면 짧은 프리뷰를 보인다. 마우스 오버만으로 긴 정보를 전달하지 않는다. 클릭하면 상세 모달 또는 우측 상세 패널을 열고, 아래 정보를 제공한다.

- 점수 산정 근거와 변화
- 확인된 강점
- 반복 오개념
- 부족한 증거
- 해당 분야의 이전 문제·실습·답안
- 추천 문제와 복습 일정

## 3. 역량 분류 체계

초기 분야는 다음 6개 그룹으로 표시한다. DB에서는 세부 skill code를 유지하고 UI에서만 그룹화한다.

| UI 그룹 | 세부 역량 예시 | 초기 색상 |
|---|---|---|
| 웹·API 보안 | API_SECURITY, XSS_CONTEXT, SQLI_QUERY, FILE_UPLOAD, SSRF | 빨강 |
| 인증·인가 | AUTHENTICATION, AUTHORIZATION, SESSION_COOKIE, CSRF | 보라 |
| 서버·운영 | LINUX_SERVER, NETWORK_TLS, DOCKER_DEPLOY, SECRETS_MANAGEMENT | 주황 |
| 개발·데이터 | JAVA_SPRING, WEB_ARCHITECTURE, SQL_DML, DATA_MODELING | 파랑 |
| 분석·검증 | DEBUGGING, STATIC_DATA_FLOW, DATA_QUALITY | 청록 |
| 보고·설계 | REPORTING, REQUIREMENTS | 초록 |

새 분야는 기존 코드의 이름을 바꾸지 않고 새 skill code를 추가한다. 과거 기록의 의미가 변하지 않게 하기 위해서다.

## 4. 데이터 모델

모든 테이블은 `AppUser`와 연결한다. 현재 개발 모드에서 자동 생성되는 Owner도 일반 사용자와 같은 모델을 사용한다.

### 4.1 평가와 근거

| 테이블 | 핵심 필드 | 목적 |
|---|---|---|
| `competency_assessment` | id, user_id, skill_code, score, confidence, status, rationale, evidence_count, assessed_at, assessment_version | 현재·과거 역량 평가 |
| `competency_evidence` | id, assessment_id, source_type, source_ref, observation, reviewer, confidence, created_at | 점수의 근거 추적 |
| `competency_gap` | id, user_id, skill_code, kind, statement, severity, status, discovered_at, resolved_at | 오개념·증거 부족·훈련 공백 |
| `competency_recommendation` | id, user_id, target_type, target_id, reason, priority, status, due_at | 다음 문제·복습·실습 추천 |

`score` 범위는 0~100이다. `confidence`는 `LOW`, `MEDIUM`, `HIGH`다. 점수와 신뢰도는 독립이다.

### 4.2 케이스와 버전

| 테이블 | 핵심 필드 | 목적 |
|---|---|---|
| `training_case` | id, slug, title, case_type, status, primary_skill_code, difficulty, created_at | 훈련 케이스의 고정 식별자 |
| `training_case_version` | id, case_id, version, prompt_md, assets_manifest, rubric_json, expected_evidence_json, release_state | 문제·정답 기준의 불변 버전 |
| `training_case_skill` | case_version_id, skill_code, weight | 한 케이스의 다중 역량 연결 |
| `training_case_prerequisite` | case_version_id, prerequisite_skill_code, min_score | 응용 문제의 선행 조건 |
| `training_case_variant` | base_case_version_id, variant_case_version_id, variant_kind | 기본·응용 문제 연결 |

`case_type`은 `STATIC_DIAGNOSIS`, `REPORT_REVIEW`, `LAB` 중 하나다. 케이스를 수정하면 반드시 새 `training_case_version`을 생성한다.

### 4.3 시도·피드백·산출물

| 테이블 | 핵심 필드 | 목적 |
|---|---|---|
| `training_attempt` | id, user_id, case_version_id, parent_attempt_id, status, started_at, submitted_at, score, result_state | 한 번의 풀이 기록 |
| `training_answer` | attempt_id, diagnosis_state, evidence_md, root_cause_md, remediation_md, verification_plan_md, private_note_md | 구조화된 답안 |
| `training_feedback` | attempt_id, source, verdict, strengths_json, issues_json, missing_evidence_json, next_steps_json, model_metadata | 루브릭·AI 피드백 |
| `training_artifact` | attempt_id, kind, safe_path, sha256, original_name, created_at | 로그, 스크린샷, 제출 파일 |
| `training_bookmark` | user_id, case_id, folder_name, memo, created_at | 보관함과 개인 분류 |

과거 답안은 수정하지 않는다. 재시도는 `parent_attempt_id`로 연결한다. 이전 답안 비교 화면은 두 attempt를 나란히 읽기 전용으로 보여준다.

### 4.4 실습 인스턴스

| 테이블 | 핵심 필드 | 목적 |
|---|---|---|
| `lab_definition` | id, case_version_id, compose_template_path, reset_strategy, max_duration_minutes, network_policy | 실행 가능한 격리 실습 정의 |
| `lab_instance` | id, user_id, lab_definition_id, attempt_id, state, started_at, expires_at, stopped_at, reset_count | 사용자별 실행 인스턴스 |
| `lab_event` | id, lab_instance_id, event_type, message, created_at | 시작·중지·초기화·오류 감사 로그 |

실습 컨테이너는 외부 인터넷으로 나가지 않는 전용 Docker 네트워크에 둔다. 호스트 파일 시스템은 읽기 전용 자료 폴더 외에 마운트하지 않는다. 실습 종료·만료·초기화 시 데이터 볼륨을 삭제하고 새 인스턴스를 생성한다.

## 5. 문제 형식과 채점 기준

### 5.1 모든 문제의 공통 답안 양식

사용자는 아래 항목을 분리해 작성한다.

```text
1. 판정: 취약 / 정상 / 추가 증거 필요
2. 근거: 코드 위치, 요청·응답, 로그, 설정
3. 성립 조건: 인증 상태, 역할, 입력값, 배포 조건
4. 영향 범위: 가능한 영향과 제한 조건
5. 원인: 신뢰 경계와 데이터 흐름
6. 조치: 코드·설정·운영 계층별 조치
7. 재검증: 정상·악성·경계 조건의 테스트 계획
```

판정을 `추가 증거 필요`로 제출하는 것을 오답 처리하지 않는다. 증거 부족 상황에서 단정하지 않는 판단은 진단 역량이다.

### 5.2 정적 진단 문제

코드 일부, HTTP 요청·응답, 로그, 설정, 스키마 일부를 제공한다. 실행 환경이 없어도 풀이 가능해야 한다.

초기 20개 케이스의 목표 분포는 다음과 같다.

| 분야 | 수 | 예시 |
|---|---:|---|
| 인증·인가 | 5 | IDOR, BOLA, 관리자 기능 인가 누락, 세션 고정 |
| SQLi·XSS | 4 | MyBatis 동적 쿼리, LIKE 조건, 출력 컨텍스트, 오류 노출 |
| 업로드·경로 | 3 | 파일 유형, 저장 경로, 다운로드 소유권, Path Traversal |
| SSRF·리다이렉트 | 3 | URL 검증, DNS 재해석, 리다이렉트, 프록시 오탐 |
| 서버·배포 | 3 | Docker 비밀값, CI 설정, TLS, 기본 파일 노출 |
| 보고서 리뷰 | 2 | 과장 영향, 부족한 증거, 잘못된 해결방안 |

### 5.3 보고서 리뷰 문제

의도적으로 잘못된 보고서를 제공하고, 사용자는 오류를 찾고 수정한다. 필수 판정 대상은 다음이다.

- HTTP 상태 코드 하나만으로 취약점 단정
- HTTP 메서드 존재만으로 위험 단정
- JWT 응답 포함만으로 취약점 단정
- 경로 숨김을 인가 통제로 오인
- 증거 없이 영향도 과장
- 입력 필터링만 적고 인코딩·권한·재검증을 누락

### 5.4 격리 실습 문제

실습은 다음 다섯 개로 시작한다.

1. 객체 수준 인가 누락
2. 파일 업로드 저장 경계
3. URL 입력과 SSRF 방어
4. Spring Security 인가 누락
5. Docker·CI 비밀값 관리

각 실습은 하나의 핵심 목표만 가진다. 전체 쇼핑몰·커뮤니티 같은 대형 예제 사이트를 새로 만들지 않는다.

## 6. 채점과 피드백

### 6.1 점수 모델

한 시도의 점수는 아래 요소를 합산한다.

| 요소 | 비중 | 판정 방식 |
|---|---:|---|
| 취약 여부 판정 정확도 | 20 | 루브릭의 허용 결론과 비교 |
| 증거의 구체성 | 20 | 코드·패킷·로그·설정 위치 존재 여부 |
| 원인 분석 | 20 | 신뢰 경계와 데이터 흐름 연결 여부 |
| 조치안 현실성 | 20 | 코드·설정·운영 계층의 적합성 |
| 재검증 계획 | 15 | 정상·악성·경계 입력 포함 여부 |
| 보고 품질 | 5 | 과장, 불명확한 용어, 비밀값 노출 여부 |

분야 점수는 최근 시도 가중치, 난이도, 응용 문제 성공, 반복 오개념을 조합해 갱신한다. 단일 문제를 맞혔다고 큰 폭으로 올리지 않는다.

### 6.2 피드백 형식

피드백은 아래 필드를 반드시 포함한다.

```text
판정: 정확 / 부분 정확 / 증거 부족 / 오판
맞은 근거
틀리거나 불완전한 근거
누락된 증거
오개념
수정 방향
다음 추천 문제
```

금지 표현은 `잘했습니다`, `조금 더 보완하세요`처럼 판정 근거가 없는 문장이다.

### 6.3 AI 모델 역할

| 역할 | 모델 사용 | 제한 |
|---|---|---|
| 대량 문서·로그 분류 | Gemini Flash | 정답 확정 금지 |
| 답안 반례·설명 검토 | GPT 또는 Claude | 루브릭 결과를 덮어쓰지 않음 |
| 코드 조치안 비교 | DeepSeek 또는 GPT | 코드 실행 결과를 임의로 주장하지 않음 |
| 최종 점수 | 규칙 엔진 | 모델의 장문 추론을 점수 근거로 사용하지 않음 |

모든 모델 호출은 제공자, 모델명, 입력·출력 토큰, 추정 비용, 프롬프트 템플릿 버전만 저장한다. API 키, 원문 비밀값, 내부 추론 과정은 저장하지 않는다.

## 7. API 계약 초안

| HTTP | 경로 | 용도 |
|---|---|---|
| GET | `/api/training/dashboard` | 카드, 추천, 최근 활동, 변화 요약 |
| GET | `/api/training/skills/{code}` | 분야 상세, 근거, 오개념, 기록 |
| GET | `/api/training/cases` | 문제 보관함 필터·정렬·페이지네이션 |
| GET | `/api/training/cases/{caseId}` | 문제 버전과 제출 가능한 자료 |

| PUT | `/api/training/attempts/{attemptId}/answer` | 임시 저장 |
| POST | `/api/training/attempts/{attemptId}/submit` | 루브릭 검사와 피드백 생성 요청 |
| GET | `/api/training/attempts/{attemptId}` | 답안·피드백·산출물 조회 |
| GET | `/api/training/attempts/{attemptId}/compare/{otherAttemptId}` | 이전 답안 비교 |

모든 API는 로그인 사용자의 데이터만 반환한다. 관리자 기능은 케이스 발행·루브릭 관리·실습 정의 관리로 한정한다.

## 8. 보안·운영 요구사항

1. API 키는 `.env` 또는 AWS Secrets Manager에만 둔다. 프런트엔드 번들·DB·Markdown·오류 메시지에 기록하지 않는다.
2. 과거 자료에서 발견된 자격 증명은 평가 근거로만 다루고 값은 이관하지 않는다.
3. 실습 컨테이너는 외부 공개하지 않으며, 고유 네트워크와 만료 시간을 가진다.
4. 실습 컨테이너는 Docker 소켓, 호스트 네트워크, 호스트 홈 디렉터리, 실제 클라우드 자격 증명을 마운트하지 않는다.
5. 업로드 산출물은 크기·확장자·MIME를 검증하고 사용자 전용 경로에 저장한다.
6. 답안 및 피드백의 비밀값 패턴은 저장 직전 마스킹한다.
7. 평가 API에는 사용자별 요청 제한을 둔다. 모델 호출은 중복 제출 방지 키를 사용한다.
8. 점수 변경은 감사 로그에 이전 값·새 값·근거·평가 버전을 남긴다.

## 11. 작업 단위와 검토 규칙

각 구현 단위는 하나의 목적만 가진다. 예시는 다음과 같다.

```text
작업: competency_assessment 엔티티와 Repository 추가
검증: 마이그레이션, CRUD, 사용자 분리 Repository 테스트
검토: DB 스키마와 API 응답 확인
다음 작업: competency_evidence 추가
```

한 작업에 엔티티, API, 화면, AI 호출, Docker 실습을 함께 넣지 않는다. 리뷰 범위가 커져 오류를 찾기 어려워지기 때문이다.

## 12. 현재 단계의 결정 사항

현재 완료한 것은 단계 0의 계획 문서화다. 코드 구현은 시작하지 않는다. 다음 단계는 단계 1의 영속 데이터 기반이며, 시작 전 다음 항목을 다시 확인한다.

1. 최종 메뉴 이름: 기본값은 `역량강화`
2. 실습 기능은 단계 5까지 보류
3. 초기 문제 20개는 정적·보고서 리뷰 문제부터 작성
4. AWS는 초기 단계에서 필수가 아니며, MySQL·Docker 로컬 구성이 먼저다
5. Claude·GPT·DeepSeek·Gemini API는 단계 4에서만 연결한다
