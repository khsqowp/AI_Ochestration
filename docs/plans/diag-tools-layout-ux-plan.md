# 진단 도구 레이아웃·UX 재설계 계획

## 범위와 판정 기준

- 시작: 인코더·디코더 4종, HAR/JS 경로 도구 3종, Burp 자매 도구 2종의 현재 화면 구조와 공통 셸을 감사한다. 끝: 아래 순서대로 구현할 수 있는 레이아웃 및 증적 캡처 설계를 확정한다. 이 문서는 구현 결과가 아니다.
- 최우선 판정: 같은 창 크기·브라우저 배율 100%에서 HAR/JS 결과 트리의 **실제 보이는 높이와 폭이 감소하지 않아야** 한다. HAR 분석 → 필터 → 경로 확인 중 브라우저 줌 축소·복귀가 필요 없어야 한다. 인코딩/디코딩 입력→출력 확인과 증적 수집도 한 작업 화면에서 끝나야 한다.
- 수치의 성격: 아래 px/%는 코드의 `padding`, `margin`, `font-size`, `min-height`, `vh`로 계산한 **800px 높이 뷰포트 기준 추정**이다. 화면 캡처나 실측값은 아니다. 줄바꿈, 운영체제 글꼴, 상단 앱 셸 높이에 따라 달라진다. 구현 전후에는 동일한 800px/1080px 높이와 1280px/1440px 너비, 100% 배율에서 DOM 사각형과 내부 스크롤 위치로 측정한다.

## 1. 현황 감사

### 1순위 문제: HAR 엔드포인트 트리의 겹친 머리말

`frontend/src/pages/RouteTreeToolPage.tsx:13-24`가 React `sheet-header`의 eyebrow+`h2`, `diag-warning`, 폐쇄망 다운로드 줄, iframe을 이 순서로 그린다. 그런데 `frontend/public/diagnostics-fixtures/route-tree-tools/har-endpoint-tree.html:66-69`는 iframe 첫머리에 `<h1>`과 긴 사용 설명을 다시 그린다. 내부 `h1`은 30px/36px 행 높이와 아래 여백 8px이고, `main`의 위·아래 패딩은 28px/60px이다(`har-endpoint-tree.html:11-14`). 외부 경고는 10px 상하 패딩과 11.5px 글자, 다운로드 줄은 9px 상하 패딩을 쓴다(`frontend/src/styles.css:889,933-937`). 제목·설명·다운로드와 관련 여백만 합쳐도 **대략 210~300px, 800px 화면의 약 26~38%**를 트리 위에서 소비할 수 있다. 설명 줄바꿈이 늘면 더 커진다. 이것이 사용자가 브라우저 배율을 줄였다 되돌리는 핵심 원인이라는 가설이며, 정확한 비율은 실측이 필요하다.

## 2. 제안하는 통일 레이아웃 패턴

**한 화면에 제목은 한 곳.** 앱 안에서는 React `sheet-header`를 유일한 페이지 제목으로 두고, iframe 내부 `h1`과 반복 설명은 제거한다. 외부 경고는 한 줄 상태/안내로 압축하되 승인 범위와 브라우저 로컬 처리 사실은 유지한다. 내부 도구가 독립 HTML로 다운로드되어 열릴 때에는 작은 독립 실행 머리말과 원래 안전 안내를 보여준다. 이는 iframe 파일 자체가 폐쇄망에서도 이해 가능해야 하기 때문이다. 내부 `h1`의 표시 여부는 parent의 통제된 `postMessage` 임베드 모드 신호 또는 명시적인 URL 모드로 선택하고, 초기값은 독립 실행 모드로 둔다. Burp·경로 5개 HTML에 공통 적용한다. **Simplicity/타이포 위계/Craft**: 한 번만 읽는 제목, 작업과 관계없는 반복 설명 제거, 독립 실행 맥락 보존.

**작업 순서를 화면 순서로.** 상단 1줄에는 현재 도구명·`진단 도구`로 돌아가기·인접 도구 전환(스마트 디코더↔트리↔레인보우/JWT, HAR↔JS↔체크리스트)·오프라인 다운로드를 놓는다. 현재 `/dashboard/diag/:toolId` 주소와 `DiagToolPage` 분기(`frontend/src/pages/DiagToolPage.tsx:28-31`)는 유지하고 링크만 제공한다. 도구 전환 전 미내보낸 증적이 있으면 상태 유지 또는 확인을 제공한다. **Wayfinding**: 위치·다음 도구·나가는 길을 한 줄에서 알 수 있다.

**상단 입력은 필요한 만큼, 결과는 남은 공간 전체.** HAR은 파일 선택+분석/초기화를 1줄 또는 작은 2줄로 만들고, 결과 보기 탭·검색·제외·범위·펼치기/접기는 트리 바로 위의 고정 도구막대에 둔다(`har-endpoint-tree.html:69-86`). JS는 파일/붙여넣기 입력 중 사용 중인 쪽만 기본 노출하고 150px 입력은 사용자가 펼쳐 늘리게 한다(`js-route-tree.html:58-69`). 중요한 입력을 숨겨 접근성을 낮추지 않도록 파일 선택과 붙여넣기 전환을 명시한다. 체크리스트는 카테고리와 선택 목록을 넓은 화면에서 좌우 두 창으로 놓고 미리보기가 카테고리 길이에 밀리지 않게 한다. Burp History는 표와 선택 상세를 좌우 또는 하단 분할창으로, Comparer는 두 입력과 양쪽 결과를 대응 위치에 둔다. 스마트 디코더는 입력과 현재 단계 결과를 좌우(좁은 화면 세로)로, 트리는 입력/필터 옆에 독립 트리 창을 둔다. JWT/레인보우의 고급 조작·옵션은 현재 모드 옆에서 펼치고 결과·진행은 항상 눈에 남게 한다. **Grouping & mapping/Simplicity**: 컨트롤을 영향받는 결과 가까이에 둔다.

**높이 계약.** 앱 페이지→`PanelShell`→`.tool-modal-body`→`.diag-scanner-list`→iframe까지 높이 기준을 연속시킨다. 각 레벨에 `display:flex` 또는 `grid`, 남은 영역에 `flex:1 1 auto` 또는 `grid-template-rows:auto minmax(0,1fr)`, 스크롤 경계마다 `min-height:0`, 실제 결과 창에만 `overflow:auto`를 준다. iframe의 `height:min(80vh,920px)`를 페이지 기준 남은 높이로 대체하고, 내부 HTML은 `height:100dvh`의 `main`에서 입력 `auto`, 결과 `minmax(0,1fr)`로 나눈다. 내부 `.table/.tree/.table-wrap`의 현재 `min-height:400px/260px`는 작은 화면에서 전체 페이지를 넘기지 않도록 화면 크기별로 재검토하되, 800px 데스크톱에서 실제 가시 결과 높이는 기존보다 커야 한다. 현재 DOM에 없는 `.diag-scanner-card`를 대상으로 한 iframe 신장 규칙(`styles.css:1029-1030`)에 기대지 않는다. 모달과 embedded의 높이/폭 계약을 각각 확인한다. **Craft**: 고정 `vh` 추측을 없애고 실제 컨테이너의 남는 공간을 배분한다.

**측정 목표와 검증.** 800px 높이/100% 배율에서 HAR의 제목·안내·다운로드 합계는 약 60~90px 이내를 목표로 하고, 결과 트리의 가시 높이를 현재 실측값보다 최소 120px 늘리는 것을 1차 목표로 둔다. JS 트리와 두 Burp 결과는 각각 이전 실측값 이상이어야 한다. 1280px 폭에서는 HAR 트리의 730px 최소 표 너비(`har-endpoint-tree.html:28,31`)가 잘리거나 페이지 전체에 수평 스크롤을 만들지 않아야 한다. 좁은 폭에서는 도구막대가 줄바꿈되더라도 결과 창 최소 사용 공간을 확보하고 표 내부에서만 가로 스크롤한다. 결과가 많거나 긴 문자열, 파일 선택 전/후, iframe 독립 실행, 모달/embedded, 키보드 접근, 브라우저 줌 100%를 검증한다. UI 실측 없이 위 목표 달성으로 간주하지 않는다.

## 3. 증적 캡처 기능 설계 제안

**첫 적용은 스마트 디코더.** 현재 `decoder.tsx:273-283,298-345`에 자동 연쇄 단계, 최종 편집값, 재인코딩값이 이미 분리되어 있어 단계별 입력→출력 쌍을 정확히 뽑을 수 있다. 지금 관련 기능이 있다는 주장은 하지 않는다. 이 대상 코드와 경로 HTML의 문자열 검색에서는 캡처 UI/저장소가 확인되지 않았으므로 **새 기능**으로 설계한다.

1. 감지된 각 단계의 출력 행 옆에 `증적에 추가`를, 최종 디코딩 결과·재인코딩 결과 옆에도 같은 단추를 둔다. 누르면 그 시점의 입력, 변환명/단계 번호, 출력, 사용자 편집 여부, 캡처 시각, 출처 도구, 선택 메모를 하나의 항목으로 복제한다. 후속 입력 변경이 기존 캡처를 덮어쓰지 않는다. 실패 결과는 실패 상태로 명시하고 성공 증적으로 오인되지 않게 한다.
2. 데스크톱에서는 결과 오른쪽의 접이식 증적 패널을 기본 닫힘/좁은 레일로 두고, 열 때는 결과의 **기존 최소 가시 폭·높이를 침범하지 않도록** 오버레이 또는 사용자가 조절하는 분할창으로 띄운다. 좁은 화면은 하단 시트로 열어 결과를 다시 확인할 수 있게 한다. 패널에는 순서 변경, 메모 수정, 개별 삭제, 전체 복사, Markdown/CSV 다운로드를 둔다. 복사는 보기 좋은 Markdown, CSV는 따옴표·줄바꿈을 올바르게 이스케이프한다. 민감 입력이 포함될 수 있으므로 내보내기 전 선택 항목 미리보기와 수동 마스킹 편집을 제공한다.
3. 초기 저장 범위는 브라우저 탭의 현재 작업 세션으로 하고 서버 전송은 두지 않는다. 새로고침/도구 이동 시 보존이 요구되면 IndexedDB 등 브라우저 로컬 저장을 명시적으로 선택하고 지우기 동작을 제공한다. 영속성 결정 전에는 `내보내기 전 이탈` 안내를 둔다. 이미지 스크린샷은 이번 첫 단계 필수가 아니다. 기능 명칭은 데이터의 입력→출력 **기록**임을 분명히 하고, 검증되지 않은 실행/취약점 증명으로 표시하지 않는다.
4. 두 번째 적용은 스마트 디코더(트리)의 선택 노드에 조상→자식 변환 경로와 입력/출력 쌍을 보내는 동작이다(`decoderTree.tsx:68-85`). JWT의 Header/Payload, 레인보우의 검증/크랙 결과는 출처·상태를 구분해 뒤따른다. 각 도구의 출력 근처에 단추를 둬 단계별 흐름을 유지한다.
5. HAR/JS 경로 점검에서는 트리 행의 경로·호스트·메서드·관찰/후보 구분·원본 파일명을 선택해 `증적에 추가`를 제공한다(`har-endpoint-tree.html:79-86`, `js-route-tree.html:65-69`). HAR의 실제 요청과 JS 추출 후보는 다른 출처 상태로 기록한다. 공통 경로 체크리스트의 항목은 **검증 전 후보**로만 기록한다(`common-path-checklist.html:59`). 경로를 선택한 뒤 스마트 디코더에 전달하는 빠른 이동은 URL 같은 값에만 적용하며, 입력 상태 전달과 증적 저장은 별개 동작으로 둔다.

iframe은 `sandbox="allow-scripts allow-downloads allow-popups"`이고 `allow-same-origin`이 없다(`RouteTreeToolPage.tsx:24`). 따라서 React가 iframe DOM을 직접 읽는 연결을 전제로 하지 않는다. 구현 시에는 필요한 행 데이터만 `postMessage`로 보내고 `event.source`·메시지 종류·스키마·길이를 검증한다. opaque origin(`null`)을 출처 신뢰 근거로 쓰지 않는다. 독립 HTML은 부모 앱 없이도 경로 복사/내보내기가 작동해야 한다. 원본 HAR/JS 파일 전체나 인증 헤더/쿠키를 자동으로 증적에 싣지 않는다. **Grouping & mapping/Craft**: 선택 행 바로 옆에서 캡처하고, 출처와 한계를 항목 안에 남긴다.

## 4. 도구별 우선순위·리스크·작업량

작업량은 구현·화면 검증을 포함한 상대 추정이며 실제 일정은 아님. 순서는 작업 공간 개선과 증적/경로 점검의 가치에 따른다.

| 순위 | 대상 | 구현 단위 | 기대 효과 | 주요 리스크 | 작업량 |
|---:|---|---|---|---|---|
| 1 | HAR 엔드포인트 트리 + `RouteTreeToolPage` 공통 높이 | 중복 머리말 제거, 다운로드 이동, iframe/트리 높이 계약, 필터 툴바 압축 | 줌 왕복의 직접 원인 제거; 트리 가시 높이 최대 증가 | 오프라인 HTML 설명 소실, iframe/부모 이중 스크롤, 작은 화면 730px 표 | 중 |
| 2 | 스마트 디코더 | 입력·단계 결과 재배치, 단계별 증적 패널과 Markdown/CSV/복사 | 우선 워크플로우인 인코딩/디코딩 기록 완성 | 민감 값 내보내기, 재계산 후 캡처 스냅샷 일관성 | 상 |
| 3 | JS URL · API 경로 트리 | 머리말·입력 패널 압축, 트리 높이 확장 | 파일 경로 점검의 보이는 영역 확대 | 붙여넣기 접근성, 긴 입력의 스크롤 | 중 |
| 4 | 스마트 디코더(트리) | 독립 트리 창, 선택 경로 캡처 | 큰 변환 트리 탐색·기록 | 많은 열린 노드와 긴 값의 성능/가로 넘침 | 중 |
| 5 | 공통 경로 체크리스트 | 필수 경고 유지, 카테고리·미리보기 분할 | 선택과 결과의 대응 개선 | 후보를 실제 관찰 증거로 오인 | 중 |
| 6 | Burp History 뷰어 | 중복 머리말 제거, 표/상세 분할 | 표와 원문 왕복 스크롤 감소 | 긴 원문, 모바일 분할 | 중 |

| 9 | JWT 위조/분석 | 기본 디코딩 결과 우선, 조작별 접이식 섹션 | 입력과 해당 결과의 대응 개선 | 긴 키/토큰 표시, 조작별 경고 누락 | 소~중 |

구현을 시작한다면 1번에서 실측 기준선을 먼저 기록하고, 각 단위가 끝날 때 동일 뷰포트에서 결과 영역의 폭/높이·스크롤 위치를 재측정한다. 2번의 캡처 내보내기는 다단계 변환, 편집 후 재인코딩, 줄바꿈/쉼표/따옴표 입력, 빈 값, 삭제·복사 실패를 검사한다. HAR/JS 연결은 독립 HTML 동작과 iframe 메시지 검증을 따로 검사한다.

## 5. 이번엔 안 건드릴 것

- `/dashboard/diag/:toolId` 라우팅 구조 및 ID, 전체 사이드바·전역 내비게이션 구조. 도구 안의 인접 링크만 설계한다.
- 위 9개와 무관한 진단 도구 및 전체 디자인 토큰(색상·폰트·곡률·그림자)의 재작업.
- JS 경로 추출·HAR 관계 분석·Burp 파싱·디코딩 알고리즘 자체의 판정 로직. 화면과 데이터 전달 경계만 설계한다.
- 증적의 서버 저장·공유·자동 업로드와 취약점 판정 자동화. 브라우저 내 수동 선택과 내보내기만 제안한다.

이 문서는 계획만 기술한다. 현재 화면 변경, 동작 검증, 증적 기능 구현은 수행하지 않았다.
