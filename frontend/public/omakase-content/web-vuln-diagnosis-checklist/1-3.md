# 1-3. 파라미터 값 및 히든(Hidden) 필드 조작 가능성

> API 및 웹 애플리케이션에 전달되는 파라미터 값이나 히든 필드를 위조/변조하여  
> 타인의 게시물 및 개인정보 열람, 결제금액 변경, 타인의 글 수정 등을 할 수 있는 취약점.

---

## 근본적인 원인

웹 애플리케이션의 데이터 전송에 이용되는 파라미터나 히든 필드는 언제든지 클라이언트에서 수정 가능한 데이터이기 때문에 발생함.

**구체적인 취약 패턴:**
- 상품 금액을 DB 조회가 아닌 히든 필드에 저장하여 전달 → 클라이언트가 금액 임의 변조
- 결제금액 플러스(+)를 마이너스(-)로 조작하여 환불 유도
- 인증이 필요한 기능에서 서버 발급 인증키 대신 예측 가능한 값(ID, MDN, 순번 등)을 파라미터로 사용 → 파라미터 변조로 타인 정보 열람
- URL 파라미터의 레코드 식별자(PK)를 단순 증감하여 타인 데이터 접근 (IDOR, Insecure Direct Object References)

```html
<!-- 취약: 가격을 히든 필드로 전달 -->
<input type="hidden" name="price" value="50000">
<!-- 공격자가 DevTools로 value를 1로 변경 → 1원에 구매 -->
```

```http
<!-- 취약: URL 파라미터가 예측 가능한 값 -->
GET /mypage/detail?userId=10101
<!-- userId를 10102로 변조 → 타인 개인정보 열람 -->
```

---

## 2차 피해 시나리오

- 결제금액 변조로 재화를 무상/할인 취득
- 타인의 주문 내역, 개인정보, 배송지 열람
- 타인의 게시물 수정·삭제
- 관리자 식별자 추론 후 관리자 기능 접근
- 마이너스 금액 조작을 통한 포인트·캐시 부당 적립

## 해결 및 대응방안

### ① 중요 정보는 반드시 서버 측 세션/DB에서 참조

**가격, 권한 정보, 인증 상태는 절대 파라미터·히든 필드로 전달하지 않는다.**  
상품 코드만 전달받고, 서버에서 DB 조회로 금액을 가져옴.

```java
// 취약: 클라이언트가 보낸 금액을 그대로 결제에 사용
int price = Integer.parseInt(request.getParameter("price"));

// 안전: 상품 코드로 DB에서 금액 조회
String productId = request.getParameter("productId");
int price = productDao.getPriceById(productId);  // 서버 DB 조회
```

### ② 인증된 사용자 식별은 세션 값으로만 처리 (IDOR 방지)

```java
// Java: 직접 객체 참조 취약점 대응
String sql = "SELECT * FROM useraccounts WHERE account = ?";
PreparedStatement st = connection.prepareStatement(sql);
// 취약: 파라미터 uid를 그대로 사용
// st.setString(1, request.getParameter("uid"));
// 안전: 세션에서 uid를 가져옴 → 요청자 본인 정보만 조회 가능
st.setString(1, (String) session.getAttribute("uid"));
ResultSet results = st.executeQuery();
```

```csharp
// ASP.NET: 세션 내 객체 참조
SqlCommand cmd = new SqlCommand();
cmd.CommandText = "SELECT * FROM users WHERE user_id=@user_id";
cmd.Parameters.Add("@user_id", SqlDbType.VarChar, 12);
// 취약: 요청 파라미터 사용
// cmd.Parameters["@user_id"].Value = HttpContext.Request.Params.Get("user_id");
// 안전: 로그인 세션 사용
cmd.Parameters["@user_id"].Value = Session["LoginID"].ToString();
```

```php
<?php
// PHP: 세션 내 객체 참조
session_name('user');
session_start();
$user_id = session_id();
$b = $_SESSION['pr_key'];
session_write_close();
// 이후 $b(세션 키)로 DB 조회 → 클라이언트 파라미터 신뢰 금지
?>
```

### ③ 파라미터 값 검증 기준 (Positive 방식)

가이드라인에서 제시한 파라미터 검증 기준:

| 검증 항목 | 예시 |
|----------|------|
| Null 값 허용 여부 | 필수 파라미터 null 시 예외 처리 |
| 중복 허용 여부 | 동일 요청 중복 제출 차단 |
| 숫자 범위 | 수량 1~999, 금액 0 이상 등 |
| 데이터 유형 | 문자열/정수/날짜 형식 일치 여부 |
| 명시적 형 변환 유효 범위 | `Integer.parseInt()` 실패 시 400 반환 |
| 최대/최소 길이 | 게시물 제목 최대 100자 |
| 필수/선택 파라미터 구분 | 필수 누락 시 즉시 거부 |

```java
// 서버 측 파라미터 검증 예시
String productId = request.getParameter("productId");
int quantity     = 0;
try {
    quantity = Integer.parseInt(request.getParameter("qty"));
} catch (NumberFormatException e) {
    response.sendError(400, "Invalid quantity");
    return;
}

if (productId == null || productId.isBlank()) {
    response.sendError(400, "Missing productId");
    return;
}
if (quantity < 1 || quantity > 999) {
    response.sendError(400, "Quantity out of range");
    return;
}
```

### ④ 트랜잭션 최종 처리 시점에 권한 재검증

중요 기능(결제, 정보변경, 삭제)이 실행되는 마지막 서버 로직에서 반드시 권한 확인.

```java
// 게시물 수정 요청 처리 시
String sessionUserId = (String) session.getAttribute("userId");
String boardOwnerId  = boardDao.getOwnerId(boardId);

if (!sessionUserId.equals(boardOwnerId)) {
    response.sendError(403, "권한 없음");
    return;
}
boardDao.update(boardId, content);
```

### ⑤ 불가피하게 파라미터로 중요 정보를 전달해야 하는 경우

암호화 후 전달하고, 수신 측에서 복호화·검증.

```java
// 서버에서 암호화하여 클라이언트에 전달
String encrypted = AES256.encrypt(String.valueOf(orderId) + "|" + price, SECRET_KEY);
// 결제 시 수신한 암호화 값을 복호화하여 서버 DB 값과 비교 검증
```

## 보완방안

- **2-Factor / 2-Channel 인증 권고**: 결제·회원정보 변경 등 중요 기능 수행 시 추가 인증 적용
- 인증 키 발급·관리 정책:
  - 로그인 후 예측 불가능한 랜덤 고유 인증키 발급
  - 로그아웃 시 인증키 즉시 파기
  - 인증키 Timeout 설정으로 재사용 불가 처리
- 금융 결제 시 계좌 소유주와 로그인 사용자 일치 여부 서버에서 확인
- PG사(결제대행사)와 쇼핑몰 측이 결제 완료 후 금액·주문정보를 재검증하는 로직 구현
- 서버 측 검증 로직은 반드시 Server Side Language(PHP, ASP, JSP, Java 등)로 구현 — JavaScript(클라이언트)로만 검증하는 것은 우회 가능하므로 불충분
