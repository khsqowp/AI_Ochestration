# 1-2. 삽입(Injection) 공격 가능성

> 웹 애플리케이션이 사용자 입력값을 검증 없이 인터프리터(DB, OS, XML 파서 등)에 전달할 때,  
> 입력값이 명령어·쿼리 구조의 일부로 해석되어 발생하는 취약점 군.

---

## 1. SQL Injection

### 근본적인 원인
웹 애플리케이션이 사용자 입력값을 SQL 쿼리에 그대로 삽입할 때, 공격자가 SQL 문법 구조를 변조하여 의도하지 않은 쿼리를 실행시킴.

```java
// 취약한 코드: 문자열 직접 연결
String sql = "SELECT * FROM user WHERE id='" + userId + "' AND pw='" + pw + "'";
// userId = ' OR '1'='1 입력 시 → 전체 조회, 인증 우회
```

### 2차 피해 시나리오
- 인증 우회 (로그인 없이 관리자 접근)
- UNION 기반으로 DB 전체 데이터 탈취
- INSERT / UPDATE / DROP으로 데이터 변조·삭제
- `LOAD_FILE`, `INTO OUTFILE`로 서버 파일 읽기/쓰기
- MSSQL `xp_cmdshell` 통해 OS 명령 실행

### 해결 및 대응방안

**① PreparedStatement 파라미터 바인딩 (가장 중요)**

```java
// JDBC
String sql = "SELECT * FROM user_table WHERE id = ? AND password = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, request.getParameter("id"));
pstmt.setString(2, request.getParameter("password"));
ResultSet rs = pstmt.executeQuery();
```

**② MyBatis: `#{}` 사용, `${}` 사용 금지**

```xml
<!-- 안전: PreparedStatement 형태로 전달 -->
<select id="getUser">
  SELECT * FROM user WHERE id = #{userId}
</select>

<!-- 취약: 입력값이 쿼리에 그대로 대입됨 -->
<select id="getUser">
  SELECT * FROM user WHERE id = ${userId}
</select>

<!-- LIKE 검색 시 $ 대신 concat 사용 -->
<!-- MySQL -->
SELECT * FROM tbl WHERE column LIKE concat('%', #{value}, '%')
<!-- Oracle -->
SELECT * FROM tbl WHERE column LIKE '%' || #{value} || '%'
<!-- MSSQL/Sybase -->
SELECT * FROM tbl WHERE column LIKE '%' + #{value} + '%'
```

**③ 특수문자 필터링 (바인딩 불가 시 보조 수단)**

가이드라인 [표] 4 기준 필터링 문자:

| 필터링 문자 |
|------------|
| `'` `"` `=` `<` `>` `(` `)` |
| `union` `select` `drop` `--` `#` `;` |
| `sp_` `xp_` `cmdshell` `\` `%` |

```java
// JSP: 특수문자 필터링
public String sqlFilter(String str) {
    String[] arr = {"'", "\"", "--", "\\(", "\\)", "#", ">", "<", "=",
                    "\\*/", "/\\*", "\\+", "%", "@", ";", "\\\\", "|", "[", "]", "&"};
    for (int i = 0; i < arr.length; i++) {
        str = str.replaceAll(arr[i], "");
    }
    return str;
}
```

**④ 숫자형 파라미터는 타입 변환으로 검증**

```java
// 숫자 파라미터는 정수로 강제 변환
int pageNum = Integer.parseInt(request.getParameter("pageNum"));
```

**⑤ DB 계정 최소 권한 부여**
- 웹 애플리케이션 DB 계정에 DROP, CREATE, FILE 권한 부여 금지
- MSSQL의 경우 불필요한 프로시저 제거 (가이드라인 [표] 6 기준):
  `xp_cmdshell`, `xp_stratmail`, `xp_sendmail`, `xp_grantlogin`, `sp_makewebtask`, `xp_regread`, `xp_regwrite`

**⑥ 에러 메시지 차단**

```java
try {
    ...
} catch (SQLException e) {
    log.error("DB error", e);                        // 로그에만 기록
    throw new BusinessException("처리 중 오류 발생"); // 일반 메시지만 반환
}
```

### 보완방안
- 동적 ORDER BY 컬럼명은 바인딩 불가 → 화이트리스트 Map으로 처리
  ```java
  Map<String, String> allowed = Map.of("name", "u.name", "date", "u.createdAt");
  String col = allowed.getOrDefault(param, "u.id");
  ```
- DB 접근 로그 주기적 감사

## 2. Command Injection

### 근본적인 원인
OS 명령 실행 함수(`Runtime.exec`, `ProcessBuilder` 등)에 사용자 입력을 검증 없이 전달하거나, 셸을 통해 명령을 실행할 때 `;`, `|`, `&` 등의 연산자로 추가 명령이 삽입됨.

또한 `eval()`, `function()`, `exec()` 등 취약한 함수를 사용할 경우에도 동일한 문제가 발생함.

### 2차 피해 시나리오
- 서버 파일 삭제·변조
- 리버스 셸로 서버 원격 제어
- 내부망 횡적 이동(Lateral Movement)
- 악성코드 다운로드 및 실행

### 해결 및 대응방안

**① OS 명령 실행 자체 금지 (근본 해결)**

```java
// 파일 처리 → Java IO API로 대체
Files.copy(source, target);

// 이미지 처리 → 라이브러리로 대체
Thumbnails.of(inputFile).size(200, 200).toFile(outputFile);
```

**② 불가피 시 배열 방식으로 실행 (셸 해석기 우회 차단)**

```java
// 취약: 셸을 통해 실행 → 메타문자 해석됨
Runtime.getRuntime().exec("ping " + userInput);

// 안전: 인자를 배열로 분리 → 셸 메타문자 해석 안 됨
ProcessBuilder pb = new ProcessBuilder("ping", "-c", "4", ipAddress);
pb.redirectErrorStream(true);
Process p = pb.start();
```

**③ 입력값 특수문자 필터링**

가이드라인 [표] 7 기준 필터링 문자: `&`, `|`, `;`, `'`, `"`, `[`, `]`, `=`

```java
// 화이트리스트 방식 (IP 형식만 허용)
if (!ipAddress.matches("^\\d{1,3}(\\.\\d{1,3}){3}$")) {
    throw new IllegalArgumentException("Invalid input");
}
```

**④ eval() → JSON.parse() 대체**

```javascript
// 취약: eval()은 보안 검사 없이 코드 실행
// eval("var obj = (" + jsonStr + ")");

// 안전: JSON.parse() 사용
var obj = JSON.parse(jsonStr);
```

### 보완방안
- OS 명령 실행 함수 코드 정기 감사 (grep 기반 자동화: `grep -rn "Runtime.exec\|ProcessBuilder"`)
- 서버 프로세스 실행 계정 권한 최소화 (root 실행 금지)

## 3. XPATH Injection

### 근본적인 원인
XPATH는 XML 문서를 질의하는 언어로, SQL과 유사하게 사용자 입력을 XPATH 쿼리에 검증 없이 삽입하면 구조가 변조됨.

```java
// 취약: 문자열 연결
String query = "//user[id='" + userId + "' and pw='" + pw + "']";
// userId = ' or '1'='1 → 모든 사용자 조회, 인증 우회
```

### 2차 피해 시나리오
- 인증 우회 (XPATH 기반 로그인 로직 무력화)
- XML 문서 내 전체 데이터 열람 (사용자 정보, 설정값)
- Blind XPATH Injection으로 점진적 데이터 추출

### 해결 및 대응방안

**① 입력값 유효성 검증 및 특수문자 필터링**

가이드라인 [표] 8 기준 필터링 문자: `'`, `=`, `[`, `]`, `(`, `)`, `,`, `*`, `:`, `/`

```java
public String filterXpath(String input) {
    return input.replaceAll("[\'=\\[\\](),:*/]", "");
}
```

**② 파라미터화된 XPATH 사용 (Variable Resolver)**

```java
XPathFactory factory = XPathFactory.newInstance();
XPath xpath = factory.newXPath();

// 변수 바인딩 방식으로 구조 변조 차단
SimpleVariableResolver resolver = new SimpleVariableResolver();
resolver.addVariable(new QName("userId"), userId);
resolver.addVariable(new QName("pw"), pw);
xpath.setXPathVariableResolver(resolver);

String expr = "//user[id=$userId and pw=$pw]";
NodeList result = (NodeList) xpath.evaluate(expr, doc, XPathConstants.NODESET);
```

### 보완방안
- 민감 데이터(인증 정보 등)는 XML보다 DB에 저장하고 PreparedStatement 사용 권장

## 4. LDAP Injection

### 근본적인 원인
LDAP 검색 필터를 동적으로 생성할 때 입력값을 검증하지 않아, 공격자가 필터 구조를 변조하여 LDAP 트리를 조작함.

```java
// 취약: 필터에 입력값 직접 삽입
String filter = "(uid=" + userId + ")";
// userId = *)(uid=*)( 입력 시 → 모든 사용자 조회
```

### 2차 피해 시나리오
- 인증 우회 (인증 필터 무력화)
- LDAP 디렉터리 내 전체 사용자 정보 열람
- LDAP 트리 수정·삭제
- 고권한 계정 식별 후 권한 상승

### 해결 및 대응방안

**① 화이트리스트 기반 입력 검증**

```java
// 허용 문자만 통과 (영문·숫자·하이픈·점만 허용)
if (!userId.matches("^[a-zA-Z0-9._-]{1,64}$")) {
    throw new IllegalArgumentException("Invalid userId");
}
```

**② LDAP 특수문자 이스케이프 (RFC 4515 기준)**

가이드라인 [표] 9 기준 필터링 문자:
`'`, `"`, `--`, `#`, `(`, `=`, `*/`, `/*`, `+`, `<`, `>`, `*`, `;`, `&`, `|`, `%`, `union`, `select` 등

```java
public static String escapeLdapFilter(String input) {
    return input
        .replace("\\", "\\5c")
        .replace("*",  "\\2a")
        .replace("(",  "\\28")
        .replace(")",  "\\29")
        .replace("\0", "\\00");
}
```

**③ Spring LDAP: LdapQueryBuilder 활용**

```java
import static org.springframework.ldap.query.LdapQueryBuilder.query;

LdapQuery ldapQuery = query()
    .where("uid").is(userId)
    .and("userPassword").is(password);

List<User> users = ldapTemplate.search(ldapQuery, new UserContextMapper());
```

### 보완방안
- LDAP 연결 계정은 필요한 OU·속성만 읽기 가능하도록 ACL 최소화
- 시스템이 LDAP를 사용하지 않으면 해당 없음(N/A)으로 처리

## 5. XML eXternal Entities (XXE)

### 근본적인 원인
XML 파서가 외부 엔티티(`<!ENTITY>`) 참조를 처리할 때, 공격자가 DTD를 통해 서버 로컬 파일이나 내부 서비스를 참조하도록 유도함.

```xml
<!-- 공격 페이로드 -->
<!DOCTYPE security [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<node>&xxe;</node>
```

### 2차 피해 시나리오
- 서버 내부 파일 읽기 (`/etc/passwd`, 설정 파일, 소스코드)
- 내부망 서비스 탐색 (SSRF와 유사)
- 서비스 거부 (Billion Laughs — 재귀 엔티티 중첩)
- 클라우드 메타데이터 탈취 (`http://169.254.169.254/`)

### 해결 및 대응방안

**① XML보다 JSON 사용 권고**

가이드라인에서 가능한 경우 JSON 형태로 서버와 통신할 것을 권고함 → XXE 자체 원천 차단.

**② 외부 엔티티 및 DTD 처리 비활성화**

```java
// Java: DocumentBuilderFactory (JAXB, DOM)
DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
String FEATURE = "http://apache.org/xml/features/disallow-doctype-decl";
factory.setFeature(FEATURE, true);
DocumentBuilder builder = factory.newDocumentBuilder();
Document doc = builder.parse(new File("xmlPath"));

// ASP.NET (.NET 4.0 이전)
XmlTextReader reader = new XmlTextReader(stream);
reader.ProhibitDtd = true;

// ASP.NET (.NET 4.0 ~ 4.5.2)
XmlTextReader reader = new XmlTextReader(stream);
reader.DtdProcessing = DtdProcessing.Prohibit;

// PHP
libxml_disable_entity_loader(true);
```

**③ 입력값 화이트리스트 검증**

서버 측에서 수신된 XML의 엔티티 포함 여부 사전 검사 후 거부.

**④ SOAP 사용 시 1.2 이상으로 업그레이드**

SOAP 1.2는 외부 엔티티 허용 범위가 제한됨.

### 보완방안
- 언어·라이브러리별 상세 대응: OWASP XML External Entity Prevention Cheat Sheet 참조
- XML 파서 버전 최신 유지 (구버전 파서는 기본 설정이 취약)

## 6. SSI (Server Side Includes) Injection

### 근본적인 원인
Apache 등 웹 서버에서 SSI 기능이 활성화된 환경(`.shtml` 확장자)에서, 사용자 입력이 HTML 문서에 포함될 때 `<!--#exec -->`, `<!--#include -->` 같은 SSI 지시자가 서버에서 실행됨.

```html
<!-- 공격 페이로드 (게시판 제목 등에 삽입) -->
<!--#exec cmd="cat /etc/passwd"-->
```

### 2차 피해 시나리오
- 서버 OS 명령 실행 (Command Injection과 동일 수준)
- 서버 내부 파일 읽기
- 민감 설정 파일 노출
- 웹 서버 권한으로 악성코드 실행

### 해결 및 대응방안

**① 사용자 입력 특수문자 이스케이프**

가이드라인 [표] 10 기준 SSI 필터링 변환표:

| From | To |
|------|----|
| `<` | `&#60;` |
| `>` | `&#62;` |
| `'` | `&#39;` |
| `"` | `&#34;` |
| `#` | `&#35;` |
| `!` | `&#33;` |
| `=` | `&#61;` |

```java
// Java: SSI 특수문자 필터링
public String filterSSI(String value) {
    value = value.replaceAll("<", "&lt;").replaceAll(">", "&gt;");
    value = value.replaceAll("!", "&#33;").replaceAll("#", "&#35;");
    value = value.replaceAll("=", "").replaceAll("\"", "&#61;");
    value = value.replaceAll("--", "");
    value = value.replaceAll("exec", "");
    value = value.replaceAll("include", "");
    return value;
}
```

**② PHP: htmlspecialchars() 사용**

```php
echo htmlspecialchars($userInput, ENT_QUOTES, 'UTF-8');
```

**③ SSI 기능 비활성화 (근본 해결)**

```apache
# Apache httpd.conf
Options -Includes
```

**④ Java/Spring 환경에서는 해당 없음**

SSI는 Apache/Nginx의 정적 파일 처리 기능이며, JSP/Spring 환경에서는 동작하지 않으므로 해당 환경 사용 시 N/A 처리 가능.

### 보완방안
- SSI 사용이 필수인 경우 `exec` 지시자만 선택적 비활성화:
  ```apache
  SSIExecDisabled on
  ```
- 웹 서버 설정 정기 감사로 `Options Includes` 활성화 여부 점검

## 공통 대응 원칙 요약

| 취약점 | 핵심 대응 | 보조 대응 |
|--------|----------|----------|
| SQL Injection | PreparedStatement / MyBatis `#{}` | DB 최소 권한, 에러 차단 |
| Command Injection | OS 명령 실행 회피, 배열 방식 실행 | 입력 화이트리스트 |
| XPATH Injection | 입력 필터링, Variable Resolver | XML → DB 저장 전환 |
| LDAP Injection | 화이트리스트, 특수문자 이스케이프 | LdapQueryBuilder |
| XXE | JSON 대체, DTD 비활성화 | 파서 최신 버전 유지 |
| SSI Injection | 특수문자 이스케이프, SSI 비활성화 | Java 환경은 N/A |

> **공통 원칙**: 사용자 입력값은 절대 신뢰하지 않으며, 데이터와 명령어 구조를 분리하고, 최소 권한 원칙을 적용한다.
